## Segment 2 · Defining & calling functions, `return`, docstrings (0:08–0:24)

### Slide 5 — The unit of reuse

So: the function. Let me tell you what a function actually is before we look at any syntax, because the syntax is easy and the idea is what matters. A function is a chunk of work that you've given a name to. That's it. That's the whole idea. You take some lines of code that do a job, you wrap them up, you give them a name, and from then on you can do that job just by saying its name. It's exactly like a recipe. Writing the recipe down is one thing; cooking the meal is another. And once the recipe is written, you can cook that meal a hundred times without ever writing it out again. That's a function.

### Slide 6 — Defining and calling

Let's look at the syntax, which is beautifully simple. You write the keyword def — short for define — then the name you want to give it, then parentheses, then a colon. And then, indented underneath, the body: the actual work. Look at the example on screen. I write "def greet", open parenthesis, name, close parenthesis, colon. And indented below it, "return an f-string saying Hi, comma, name". That's a complete function. Now, some vocabulary that I want you to get right from day one, because people mix these up constantly and it causes real confusion later. The names inside the parentheses on the def line — like "name" here — those are called parameters. They're the blanks in the recipe. The actual values you supply when you use the function — like the string "Asha" — those are called arguments. Parameters are the blanks; arguments are what you fill them with. Say that to yourself a couple of times this week and it'll stick. And then the last line on the slide: message equals greet, open paren, "Asha", close paren. That's the call. That's where the function actually runs. And this is the single most important thing on this slide, so let me say it clearly: defining a function does not run it. When Python reads that def block, it does not execute the body. It just makes a note — "there's a thing called greet, and here's what it does" — and moves straight on. The body only runs when you call it, with those parentheses. That's why a beginner will sometimes write a beautiful function, run the file, see absolutely nothing happen, and wonder what went wrong. Nothing went wrong. They defined it and never called it. Defining is writing the recipe. Calling is cooking.

### Slide 7 — return and the invisible None

Now, return. Return is how a function hands a value back to whoever called it. Look at the first example: def add, a and b, return a plus b. When you call add with two and three, that return statement takes the value five and hands it back out, so you can catch it in a variable, or print it, or pass it into something else. And note something important: return also ends the function immediately. The moment Python hits a return, that function is finished — anything below it in the body simply doesn't run. Now look at the second example, and this is the part I really want you to notice, because it catches everyone. Def shout, text, and the body just does print of text dot upper. There's no return statement anywhere. So what does shout hand back? And the answer is on the slide: None. Every function in Python returns something, always, without exception. If you don't write a return, Python quietly returns None for you. If you write a bare return with nothing after it, same thing — None. So when I do repr of shout "hi", I get the string 'None' back. And this brings us to a distinction that trips up almost every single beginner, so let me be very explicit about it. Print and return are not the same thing. They are not even similar. Print puts text on the screen for a human to look at. Return hands a value back to the code that called you. If your function prints but doesn't return, you cannot do anything with its result — because its result is None. Look at it this way: print is you shouting the answer across the room. Return is you handing someone the answer on a piece of paper. If you want to use that answer for anything, you need the piece of paper. Shouting is not enough.

### Slide 8 — Docstrings and help

The last piece before we go to the demo: how does a function explain itself? And the answer is the docstring. A docstring is simply a string — usually a triple-quoted one — that you put as the very first thing in the function body. Look at the example. Def greet, with some annotations we'll come back to later, and then immediately, indented, a string in triple quotes: "Return a friendly greeting." That's the docstring. Now here's why it's special, and why it's not just a comment. Python keeps it. It attaches that string to the function itself. So when I go to the prompt and type help, open paren, greet — look what comes back. Python tells me: help on function greet in module main, then the exact signature, then my docstring, indented underneath. I never wrote any documentation system. I never installed anything. I just put a sentence at the top of my function and Python turned it into help. And remember Week 1 — on your very first day, you typed help of len, and Python told you what len does. Now you know how that worked. Somebody wrote a docstring. So please get into this habit, starting today: every function you write gets one line saying what it does. Write it in the imperative — "Return a friendly greeting", not "This function returns a greeting" — because that's the convention across the whole Python world, and matching it makes you look like you know what you're doing. Which, after today, you will. Right. Let's go and write some real functions.

## Segment 3 · Demo 9 — the argument-grammar tour (0:24–0:50)

### Slide 9 — Let's write every kind of signature

Let me share my screen. We're going to spend the next stretch on one single topic — how you describe what goes into a function — because Python gives you an unusually rich and expressive set of options here, and once you can read them all, you can read anybody's code. Watch closely, because you'll write every one of these yourself this week.

### Slide 10 — Watch this, Demo 9

Here's the plan for this demo. I'm going to start with the simplest possible function that takes an argument, and then I'm going to keep adding to it until it uses every kind of parameter Python has. So: first, positional arguments, keyword arguments, and defaults. Then star-args and star-star-kwargs, which soak up anything extra you throw at a function. Then keyword-only parameters, which force the caller to name what they're passing. Then positional-only parameters, which do the exact opposite. And then at the end I'm going to show you the single most famous trap in the entire Python language — the mutable default argument — and I'm going to show you the fix, and I'm going to show you the tool that catches it for you. Let's start simple.

### Slide 11 — Positional, keyword, default

So here I am at the prompt. Let me define greet again, but this time with a second parameter that has a default: def greet, name, comma, greeting equals "Hi". That equals sign in the def line means "if the caller doesn't give me a greeting, use Hi". Now watch how many different ways I can call this one function. First: greet of "Asha". I only passed one argument, and it went into the first parameter, name, because of its position — that's what positional means. And greeting fell back to its default. So I get "Hi, Asha!". Now: greet of "Asha", comma, "Hello". Two positional arguments now, so the first goes to name and the second goes to greeting, overriding the default, and I get "Hello, Asha!". Now watch this third one, because it's lovely. Greet, with greeting equals "Welcome", comma, name equals "Ravi". I've named both arguments explicitly — those are keyword arguments — and look, I've written them in the wrong order, greeting first and name second, and it doesn't matter at all. Python matches them up by name, not position, and I get "Welcome, Ravi!". That's a genuinely useful thing: keyword arguments make a call self-documenting and free you from having to remember the order. And finally, let me break it. Greet with no arguments at all. And Python says: TypeError, greet missing one required positional argument, name. And I want you to notice how good that message is. It names the function, it tells you exactly what's missing, and it tells you what kind of thing it is. Python's error messages are your friends — read them, don't fear them. Name had no default, so it's required. Greeting had a default, so it's optional. That's the whole rule.

### Slide 12 — star-args and star-star-kwargs

Now let's meet the two most cryptic-looking pieces of Python syntax, which turn out to be very simple once you see them run. Let me define a function called report that takes star-args and star-star-kwargs, and just tells me what it received. Now I call report with one, two, three. Look at the output: args equals the tuple one, two, three. So the single star collected every positional argument I passed — however many there were — and bundled them into a tuple called args. Now let me call it with one, two, and then mode equals "fast" and debug equals True. And look: args is the tuple one, two — just the positional ones — and kwargs is a dictionary, mode maps to "fast", debug maps to True. So the double star collected every keyword argument into a dictionary. That's the whole feature. One star means "any leftover positional arguments, as a tuple". Two stars means "any leftover keyword arguments, as a dictionary". And let me call report with nothing at all — args is an empty tuple, kwargs is an empty dictionary. It doesn't complain, because star-args and star-star-kwargs are always optional; they just come back empty. Now, one thing I want to clear up, because it confuses people for years if nobody tells them. The names "args" and "kwargs" are not magic. They're just a very strong convention. The magic is entirely in the stars. I could call them star-things and star-star-stuff and it would work identically. But please do call them args and kwargs, because every Python programmer on earth will instantly know what you mean. And when do you actually use these? When you're writing something that wraps another function and needs to pass along whatever it's given without caring what it is. You'll see it constantly in real code, and now you'll know exactly what it's doing.

### Slide 13 — Keyword-only and positional-only

Two more parameter kinds, and they're mirror images of each other. Let me define make_task: title, then a bare star, then priority equals "normal". Now, that bare star on its own, sitting there as a parameter — that looks strange the first time you see it. What it means is: everything after me must be passed by keyword. It's a fence. So priority is now what we call keyword-only. Let me prove it. I call make_task with "Buy milk" and then, positionally, "high". And it fails: TypeError, make_task takes one positional argument but two were given. And I want to point something out here, because it's a bit of a gotcha — notice the error does not say "priority is keyword-only". It says "takes one positional argument but two were given". Python is counting, and the fence means only one thing is allowed through positionally. So if you ever see that error and you're sure you passed the right number of things — go and look for a bare star in the signature. But if I call it properly, with priority equals "high", spelled out as a keyword, it works fine. So why would you ever want this? Because it makes calls readable. If you see make_task of "Buy milk", "high", True, you have no idea what "high" and True mean. But make_task of "Buy milk", priority equals "high", done equals False — that reads like a sentence. Forcing keywords is a kindness to whoever reads your code later, which is usually you, in six months. Now the mirror image. Let me define power, with base, exp, and then a forward slash as a parameter. The slash means: everything before me must be passed positionally, and must not be named. So power of two, ten works — that's a thousand and twenty-four. But watch what happens when I try power with base equals two, exp equals ten. TypeError: power got some positional-only arguments passed as keyword arguments — and it names them, base and exp. And this one isn't just a curiosity, because you have already met it. Cast your mind back to Week 1. Len. If you try to call len with obj equals a list, Python says len takes no keyword arguments. That's because len's parameter is positional-only. Lots of built-in functions are like this, and now you know why. So: the star is a fence that forces names. The slash is a fence that forbids them. And when you put a whole signature together, the order is fixed — positional-only stuff, then the slash, then normal stuff, then the star, then keyword-only stuff. You'll rarely write the full thing yourself, but you will absolutely read it, and now it won't be a mystery.

### Slide 14 — The mutable-default trap

Right. Now I'm going to show you the most famous trap in Python. Every single Python programmer gets caught by this once, and then never again, and I'd like to save you the once. Watch very carefully. I define add_item, which takes an item and a basket, and the basket has a default of an empty list. Then it appends the item to the basket and returns it. That looks completely reasonable, doesn't it? It reads as "if you don't give me a basket, start with an empty one". So let me call it. Add_item of "a". I get a list containing "a". Perfect, exactly what I expected. Now, add_item of "b". And look at what comes back. A list containing "a" and "b". Where on earth did "a" come from? I didn't pass a basket. It should have started empty. Let me do it once more — add_item of "c" — and now I've got "a", "b", and "c". My so-called empty default is filling up. So what is going on? Here it is, and this is the key sentence of this whole segment: default values are evaluated once, when the function is defined — not each time it's called. So when Python read that def line, it created one empty list, right there and then, and stapled it to the function as the default. Every call that doesn't supply a basket gets that same list. The same one. Not a copy. And every append is piling onto it. It's not a bug in Python — it's a completely logical consequence of the rule that defaults are evaluated at def time — but it is absolutely a trap, because it violates what you naturally expect. And I can even prove where it lives: if I look at add_item dot dunder-defaults, there's my list, sitting on the function object, with "a", "b" and "c" in it. The evidence is right there.

### Slide 15 — The fix, and what Ruff says

So how do we fix it? The fix is a standard Python idiom, and once you've seen it you'll recognise it everywhere. You default the parameter to None instead, and then, as the first thing in the body, you check: if basket is None, make a fresh empty list. Look at the code. Def add_item, item, basket equals None. Then: if basket is None, basket equals empty list. Then append, then return. And why does this work? Because that empty list is now created inside the body, which runs on every single call — so every call gets a brand-new list. And when I run it now: "a" gives me just "a". "b" gives me just "b". "c" gives me just "c". Fresh every time, exactly as you'd expect. And I want you to notice why we use None as the sentinel here, because it's the perfect choice: None is immutable, so it can't have this problem, and it unambiguously means "the caller gave me nothing". So the rule to carry away is simple and absolute: never use a mutable default — no lists, no dictionaries, no sets. Use None and build it inside. Now, the really good news. You don't have to spot this with your eyes forever, because Ruff can spot it for you. Watch: I run ruff check with --select B006 on the broken file, and look — B006, do not use mutable data structures for argument defaults, pointing at the exact line and column, with a help line telling me to replace it with None and initialize within the function. Ruff just did the code review for me. But — and this is important, and it's why I'm typing that flag explicitly — B006 is not one of Ruff's default rules. If I just run ruff check on that broken file with no flags, Ruff says "All checks passed" and the trap sails straight through. So you have to opt in. You either pass --select B006 like I just did, or you add it to your pyproject file so it's on for the whole project. And that's a good general lesson about linters, actually: the default rule set is deliberately small and quiet, and the really valuable checks are usually the ones you have to go and switch on.

Let's take stock, because that was a dense demo and you covered a lot of ground. We took one function and called it four different ways — positionally, with keywords, letting a default fill in, and then deliberately wrong so we could read the error. We saw star-args gather up leftover positional arguments into a tuple, and star-star-kwargs gather up leftover keyword arguments into a dictionary. And then we met the mutable default trap: one list, created once at definition time, quietly shared by every call forever — and the None-and-build-it-inside idiom that fixes it. And we saw Ruff catch it for us, provided we ask for B006 by name. If any of that went past quickly, it's all in the recording, and every bit of it is in this week's lab. ## Segment 4 · Scope & LEGB, `global` / `nonlocal`, lambdas (0:50–1:10)

### Slide 17 — Where names live

Now we come to scope. And I want to set your expectations honestly: this is the part of today that beginners find hardest, and it's also the part that, once it clicks, makes a huge amount of previously baffling behaviour suddenly make perfect sense. So if you feel a bit fogged in the next ten minutes, that's completely normal and you're in good company. Stay with me, because the payoff is real.

### Slide 18 — Local vs global

Let's start with the observation that raises the question. Look at the code. At the top of my file, outside everything, I have x equals "global x". Then I define a function called show, and inside it I write x equals "local x", and return x. Now I call show, and it gives me back "local x" — no surprise there. But then I look at x afterwards, out at the top level. And it's still "global x". Completely untouched. My function assigned to x, and the x outside didn't budge. So what happened? Here's the rule, and it's the foundation of everything else in this segment: when you assign to a name inside a function, Python makes a brand-new name that lives only inside that function. It doesn't go looking for an existing x to update — it creates its own. That name is called local, and it exists only for the duration of that one call. When the function returns, it's gone. And this is a feature, not a limitation — a really important one. It means you can write a function using variables called x and count and result without ever worrying about whether some other part of the program happens to use those names too. Your function's names are its own private business. That's what makes functions safe to reuse. Imagine if it were the other way round — if every function could reach out and stomp on everyone else's variables. Nothing would ever work. So: assignment inside a function creates a local name. Hold on to that.

### Slide 19 — LEGB, the four-step search

But that raises an obvious question. If show had only read x instead of assigning to it, what would it have got? And more generally: when Python meets a name, how does it decide what that name refers to? The answer is a four-step search with a memorable name: LEGB. Look at the table. When Python meets a name, it looks in four places, strictly in this order, and it stops at the very first place it finds it. First, L, Local: is this name assigned somewhere in the function I'm currently in? If yes, use that, stop looking. If not, second, E, Enclosing: am I a function nested inside another function, and does that outer function have this name? If yes, use it, stop. If not, third, G, Global: is it defined at the top level of this module — out in the file, outside all functions? If yes, use it, stop. And if not, fourth and last, B, Built-in: is it one of the names Python gives you for free — len, print, range, sum, all of those? If yes, use it. And if it's not in any of those four places, Python gives up and raises a NameError, which is Python's way of saying "I have literally never heard of this word". Local, Enclosing, Global, Built-in. Innermost outwards. And here's the practical intuition: the closer a name is to where you're standing, the more it wins. A local x always beats a global x. And that also explains something you might have wondered about — why you shouldn't call your variable "list" or "sum". If you do, your global name will shadow the built-in one, because G comes before B, and suddenly the real list function is unreachable. LEGB explains it perfectly.

### Slide 20 — global, rare and loud

So what if you genuinely do want a function to change a module-level variable? Because we just established that plain assignment won't do it — it'll make a local instead. The answer is the global keyword. Look at the example: debug equals False at module level. Then inside enable_debug, I write "global debug" — that line is a declaration, not an assignment; it says "when I say debug in this function, I mean the module-level one, not a new local" — and then debug equals True actually updates the real thing. And it works. Debug is False before and True after. But look at the tone of this slide, because I want to be straight with you: this is rare, and it's loud. Loud because it's shouting "I am reaching outside my own function and changing shared state". Rare because you should almost never need to. The problem is that a function which quietly reaches out and changes a global is a function you cannot reason about on its own. You can't look at it and know what it does — you have to know what else in the program touched that global first. And you can't test it in isolation. And when something's wrong with debug, you have to hunt through every function in the file to find who set it. Whereas a function that just takes what it needs and returns a value can be understood by reading nothing but the function itself. So the guidance is: reach for global rarely and deliberately, and if you find yourself using it a lot, that's usually a nudge that the thing you're mutating should be a parameter and a return value instead. Know it, recognise it in other people's code, but don't reach for it first.

### Slide 21 — nonlocal, the counter closure

Now, nonlocal, which is global's more interesting cousin. Where global means "reach all the way out to the module level", nonlocal means "reach out exactly one level, into the enclosing function". And there's a beautiful little example that shows exactly why you'd want it. Look at make_counter. Inside it, I set count to zero. Then, nested inside it, I define a second function called increment, and increment says "nonlocal count", then count plus-equals one, then returns count. And then — and this is the clever bit — make_counter returns the increment function itself. Not the result of calling it. The function. So watch what happens. I say c equals make_counter, which runs make_counter once and hands me back that inner increment function, which I've named c. Now I call c, and I get one. I call c again, and I get two. Again, three. The count is remembering. It's persisting between calls. And that's remarkable, because make_counter finished running ages ago — it returned right at the start. So how is its count variable still alive? The answer is that the inner function is holding on to it. When you return an inner function that refers to a name from its enclosing scope, Python keeps that enclosing scope alive for as long as the inner function needs it. That combination — a function plus the enclosing variables it remembers — is called a closure, and it's one of the genuinely elegant ideas in programming. Now, why is nonlocal essential here? Because count plus-equals one is an assignment, and we know exactly what assignment does inside a function: it would create a fresh local count, which would break immediately. Nonlocal is what tells Python "no, I mean the count in the function wrapping me — the one that already exists". Take that word out and this stops working, and I'll show you the exact error it gives in a moment. So: global reaches all the way out; nonlocal reaches out one level. And nonlocal has a genuinely lovely use case, which global rather lacks.

### Slide 22 — Lambdas, one-expression functions

Last idea in this segment, and it's a light one after all that: the lambda. A lambda is just a tiny, throwaway function that you write inline, without giving it a def and a name. Look at the first line: double equals lambda n colon n times two. That's a function. It takes n, and it gives you back n times two. It's exactly equivalent to writing def double of n, return n times two — just squashed onto one line. Now, the rules are strict and short. A lambda takes one expression only. No statements, no if-blocks, no loops, no multiple lines. And whatever that expression evaluates to is automatically returned — you don't write return, and in fact you can't. Now, honestly? That first example, assigning a lambda to a name called double, is not how you should use them. If it needs a name, just write a def — it's clearer, and it can have a docstring. So where do lambdas actually earn their place? Look at the second example, because this is the real one. I've got a list of tasks, each a little tuple of a title and a priority number. And I call sorted on it, passing key equals lambda t colon t sub one. That key parameter says "for each item, here's how to work out what to sort by" — and my lambda says "take the thing at index one", which is the priority. And out comes the list sorted by priority: write report at one, call bank at two, buy milk at three. And if I'd written key equals lambda t colon t sub zero instead, I'd get them sorted alphabetically by title — a completely different order. That's the natural home of the lambda: a tiny, one-off rule that you need to hand to another function, that isn't worth a whole def. You'll see this constantly with sorted, and with min and max. And we'll meet it again properly when we do sorting in the next few weeks — I'm planting the seed now so it's familiar when it arrives.

## Segment 5 · Basic type hints (1:10–1:22)

### Slide 23 — Type hints

Our last concept of the day, and it's a forward-looking one: type hints. This is a modern Python habit that costs you almost nothing and pays you back constantly, and it's the foundation that the whole of Part 2's typing content is built on. So let's get the habit started right now.

### Slide 24 — Annotating parameters and returns

Look at how small this is. Def add, a colon int, comma, b colon int, close paren, arrow int, colon. That's a normal function with two little additions. After each parameter name, a colon and a type: "a colon int" says "a is meant to be an integer". And after the parentheses, an arrow and a type: "arrow int" says "this function is meant to hand back an integer". That's it. That's the entire syntax for the common case. And what have you gained? You've written down what you meant, in a place where your editor can read it. Because here's the thing about the alternative — a comment saying "a should be an integer" is just text; nothing reads it, nothing checks it, and it silently goes stale the moment someone changes the code. An annotation is structured. Your editor reads it, type checkers read it, and documentation tools read it — you saw that earlier when help printed my signature back with the annotations right there in it. It's documentation that has teeth. And to be clear: they're entirely optional. Python doesn't require them anywhere. My advice for you as beginners is to put them on your function signatures, where they do the most good, and not to agonise about anything more complicated than that for now.

### Slide 25 — Modern hint syntax

Three more pieces of syntax and you'll have everything you need for this week's lab. Look at summarise. First: titles colon list of str — written as the word list, then square brackets, then str. That says "a list whose items are strings". Same idea for counts: dict, square brackets, str comma int — "a dictionary whose keys are strings and whose values are integers". Notice you don't import anything to do this. The built-in list and dict take those square brackets directly. Second: note colon str pipe None, equals None. That vertical bar means "or". So "str pipe None" says "either a string, or nothing at all" — which is exactly what you want for an optional parameter, and it pairs naturally with a default of None, just like the fix we used for the mutable default trap. And third, a small note for anybody who goes reading older code or older tutorials this week. You will absolutely run into typing dot List with a capital L, and typing dot Optional. Those are the old spellings from before Python could do this with the plain built-ins. They still work, and nothing warns you about them — but you don't need them, and they're not what you should write in new code. Lowercase list, lowercase dict, and the pipe for "or". If you see the capitalised ones out in the wild, now you know what they are and that you have a nicer option.

### Slide 26 — Hints are not enforced

Now the single most important slide about type hints, and the one that surprises everyone coming from Java or C#. Look at what I do. I define add, annotated to take two ints and return an int. And then I call it with the strings "two" and "three". And what happens? Does it raise a TypeError? Does it complain at all? No. It returns the string "twothree" — because plus on two strings joins them, and Python cheerfully did exactly that. No error, no warning, nothing. And that's because — and this is the sentence to remember — Python completely ignores type hints when it runs your code. They are not checks. They are not enforced. The interpreter reads them, files them away where tools can find them, and then runs your code exactly as if they weren't there. Now, when I say this, the reaction is usually: well, then what's the point? And it's a fair question, and here's the answer. The point is that the payoff happens before you run. Your editor reads those hints and autocompletes properly, and underlines your mistake while you're typing it. A type checker reads them and can scan your whole project in seconds and tell you about every wrong call, without running a single line. So the hints aren't a runtime guard — they're a contract you write down so that humans and tools can hold you to it early. Catching a bug while you're typing is worth vastly more than catching it in production at two in the morning. And in Part 2 you'll take these same annotations and put a real type checker behind them and make them properly rigorous. Today we're just starting the habit. Let me show you the payoff live, because it's much more convincing than me describing it.

So, at the prompt. Let me set up the chain. At the top I define name equals "global name". Then I define outer, and inside outer I set name equals "enclosing name". This is beautiful and it's worth really understanding. When Python compiled that function, it saw an assignment to count — count is on the left of an equals sign. So it fails. And notice it doesn't fall back to the global count. It never even looks. The assignment made it local, and local it stays.
